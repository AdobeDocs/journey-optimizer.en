01 Overview

What Access Control Does (and Why It Matters)

You've just onboarded a new campaign manager and handed them access to Adobe Journey Optimizer — then realised they can accidentally publish journeys, delete content, or view data they shouldn't. Setting up access control properly from day one prevents exactly this. It's not just security hygiene; it's the difference between a team that moves fast with confidence and one that's constantly cleaning up unintended changes.

Access control in Adobe Journey Optimizer lets you define who sees what, who can do what, and in which environments — all without touching code. You control it entirely through the Permissions interface in Adobe Experience Cloud.

In this guide, you'll:

  • Understand how the permission system is structured — Admin Console, Permissions, roles, and sandboxes
  • Learn the five key concepts you'll see every time you assign access
  • Walk through the full configuration — from creating a role to adding a user in under 10 minutes
  • Explore real-life scenarios — campaign managers, contractors, and multi-team setups
  • Try it hands-on — set up a Campaign Manager role yourself with a practice scenario

Assign your first role in Adobe Journey Optimizer and take full control of who can create, edit, and publish journeys and campaigns.

03 Concepts

Before You Start: Key Concepts

Before you configure access control, here are the terms you'll see in the Adobe Journey Optimizer UI — and what they mean.

Roles

A role is a collection of permissions and sandbox assignments given to a group of users. Think of it as a job profile — "Campaign Manager", "Journey Viewer", "Content Editor". Every user in Adobe Journey Optimizer must belong to at least one role to access the product.

Permissions → Roles

Permissions

Permissions are the individual rights assigned to a role — for example, Manage Journeys or View Campaigns. They are grouped by resource (Journeys, Campaigns, Messages, Reports…). You assign permissions to roles, not directly to users.

Permission Levels

Each resource has two levels: Manage (full create/edit/delete access) and View (read-only). Some resources have additional granular permissions like Publish. Always grant the lowest level that lets the user do their job.

Attribute-based Access Control

Lets you restrict access to specific schema fields or dataset attributes using labels. Useful for protecting sensitive personal data — for example, ensuring only certain roles can see a customer's health or financial data fields in personalisation.

Full guide →

Object-level Access Control

Lets you apply labels to individual objects — a specific journey, campaign, or message — to restrict who can open or edit that object. This is on top of role-level permissions. A user needs both the right role permission and the right object label to access a labelled object.

Full guide →
Not sure whether to use a built-in or custom role?

Start with built-in roles — Adobe Journey Optimizer ships with a set of pre-configured roles (Journey Manager, Journey Viewer, Campaign Manager, Campaign Viewer) that cover the most common team setups. If a built-in role has one or two permissions you don't want users to have, create a custom role by duplicating and editing it rather than starting from scratch. Custom roles are only worth the maintenance overhead when your team's workflow genuinely diverges from the built-in structure.

04 Configure

Configure Access Control: Step by Step

By the end of these steps you'll have a role configured with the right permissions and sandboxes, and a user assigned to it — ready to log in with the correct access.

01

Open the Permissions interface

▸ Adobe Experience Cloud → Permissions → Roles

Navigate to experience.adobe.com, select the Permissions app from the product switcher, then click Roles in the left navigation. You need Product Administrator or System Administrator privileges to access this area.

📸Permissions → Roles
The Roles tab lists all built-in and custom roles. Built-in roles show a lock icon and cannot be deleted.
02

Select or create a role

▸ Permissions → Roles → [Select role] or Create role

To use a built-in role, click on it (for example Journey Manager or Campaign Manager). To create a custom role, click Create role, enter a name and description, and save. Start from a built-in role as your reference point before building from scratch.

See all built-in roles →
03

Edit permissions for the role

▸ Role dashboard → Edit → Resources panel

Click Edit on the role dashboard. The Resources panel on the left lists every resource in Adobe Journey Optimizer (Journeys, Campaigns, Messages, Reports, Administration…). Drag a resource into the role to add its permissions, then expand it to choose between Manage and View levels. Remove a resource by dragging it back out.

📸Role Edit — Resources panel
Drag-and-drop resource permissions into the role. Expand each resource to see granular permission options like Manage, View, and Publish.
Common mistake: giving Manage when View is enough

The most frequent misconfiguration is assigning Manage for resources like Journeys or Campaigns to everyone "just in case". This gives users the ability to publish, delete, and modify live assets. Follow the principle of least privilege: start with View for all resources, then add Manage only for the specific resources each role actually needs to edit. The Permission levels page lists every granular right so you can review before assigning.

04

Assign sandboxes to the role

▸ Role Edit → Sandboxes tab

Switch to the Sandboxes tab while in edit mode. Select which sandboxes users in this role can access — for example Production, Dev, or a specific named sandbox. Users only see Adobe Journey Optimizer data from sandboxes assigned to their role. Assign the minimum set of sandboxes needed.

📸Sandboxes tab in Role Edit
Select sandboxes from the list. The user will only see environments listed here when they log into Adobe Journey Optimizer.
05

Save the role

▸ Role Edit → Save

Click Save to apply your permission and sandbox changes. Changes to a role take effect for all users currently assigned to it — no re-login required. Review the summary panel that appears after saving to confirm the resource list looks correct.

Editing a role affects all users in it immediately

When you add or remove a permission from a role, every user in that role gets the change in real time — without any re-login. This is intentional but easy to overlook. If you're making a significant change (like removing Manage Journeys from a role), communicate with affected team members before saving. For safe iteration, create a new custom role and test it with one user before migrating the whole team.

06

Add users to the role

▸ Role dashboard → Users tab → Add user

From the role's dashboard, open the Users tab and click Add user. Search by name or email address and select the user from the list. If the user doesn't appear, they haven't been added to the Adobe Journey Optimizer product in Admin Console yet — do that first, then return here.

📸Users tab — Add user
Search for the user by email. Added users receive an email notification with a link to log into Adobe Journey Optimizer with their new access.
07

Verify the user's access

▸ Adobe Journey Optimizer → Log in as user

Ask the user to log in and confirm they see the expected sections and sandboxes. If a permission is missing, they'll see: "You do not have permission to access this feature. Permission needed: [resource]." Note the exact resource name shown and add it to their role. For sensitive roles, test by creating a second browser profile with the user's credentials before handing over access.

💡
Tip

To quickly audit which permissions a role has, navigate to the role and click the Permissions tab without entering edit mode. This gives you a read-only summary you can share with your security team.

05 Data

Connect to Your Data

To get access control working correctly, you need to know which data constructs in Adobe Journey Optimizer map to which permission resources. Here's what to identify first — no schema-building required, just the right labels to look for in the UI.

Resources and what they protect: Each permission resource in Adobe Journey Optimizer maps to a set of UI sections and API actions. Before assigning permissions to a role, identify which of these your user needs:

  • Journeys — access to the Journeys canvas, journey creation, testing, and publishing
  • Campaigns — access to action campaigns, API-triggered campaigns, and campaign scheduling
  • Messages — access to the message library and content editor
  • Channel configurations — access to email subdomains, push credentials, SMS providers
  • Reports — access to live reports and all-time reports across journeys and campaigns
  • Administration — access to Permissions, event configuration, and data source settings

Sandbox names matter: Make sure you know the exact names of the sandboxes in your organisation before assigning them to roles. Sandbox names are case-sensitive in the Permissions UI. You can find them in Adobe Experience Platform → Sandboxes.

Labels for attribute-based access: If you're using attribute-based access control to restrict field-level data visibility, you'll need the label names applied to your schemas. These are set in Adobe Experience Platform's data governance interface (Adobe Experience Platform → Schemas → [schema] → Field labels). Match these labels when configuring access policies in Permissions.

🔍
Where to find this

To see every available permission across all resources, go to Permissions → Roles → [any role] → Edit and browse the Resources panel. Each resource expands to show the full list of granular permissions available for that area of Adobe Journey Optimizer.

06 Journeys & Campaigns

How Access Control Applies to Your Journeys and Campaigns

Every action a user takes in a journey or campaign — from opening the canvas to hitting Publish — is gated by the permissions in their role. Here's how the permission check flows from login to live activation.

🔑
User logs into Adobe Journey Optimizer

Adobe Experience Cloud reads the user's assigned role(s) and loads the permission set. The sidebar navigation renders only the sections the user has View or Manage access to.

🗂
User opens the Journeys or Campaigns list

The list shows only journeys/campaigns within the sandbox(es) assigned to the user's role. Objects in other sandboxes are invisible — not locked, just absent.

✏️
User attempts to create or edit

If the role has Manage Journeys, the Create journey button appears. Without it, the button is absent. Same pattern applies to campaigns, messages, and all other resources.

🚀
User tries to publish

Publishing a journey requires Publish journey permission (a separate right under the Journeys resource). A user with only Manage Journeys can build and save a journey but cannot activate it to production profiles. This is a common split between content creators and campaign leads.

🏷️
Object-level label check (if configured)

If the journey or campaign has an object-level access label, the system also checks whether the user's role carries a matching label policy. Both the role permission and the object label policy must pass for the user to open the object.

⚠️
Watch out

The single most common misconfiguration is missing the Publish journey permission for users who need to activate journeys. This permission is separate from Manage Journeys — check that it's included if your Campaign Leads need to go live without waiting for admin approval.

🖥Journey canvas — access gates
A user with View Journeys only will see the canvas in read-only mode — all edit controls are hidden, and the Publish button does not appear.
07 Common Scenarios

Common Ways to Use Access Control

Access control looks different depending on your team structure. These four scenarios cover the setups admins encounter most often — read the one that matches your situation and skip the rest.

Onboarding a new campaign manager

Admin onboarding a marketer

Assign the built-in Campaign Manager role to give full create/edit/publish access to campaigns and read-only access to journeys. Add the Production sandbox and any relevant development sandbox. The user gets full campaign control without touching journey configuration.

→ User can build, schedule, and activate campaigns. Cannot edit journeys.

Agency or contractor read-only access

Admin managing external partners

Create a custom role with View Journeys, View Campaigns, and View Reports only. Assign a non-production sandbox. This gives the agency visibility into performance without any risk of editing live assets. Do not assign the Production sandbox to contractor roles.

→ Contractor can review results and report on performance. No edit access anywhere.

Multi-team setup with channel ownership

Admin managing email, push, and SMS teams

Create one role per channel team: give the Email team Manage Messages + View Journeys; give the Push team the same for push-specific channel configurations. Each team manages their own channel but cannot interfere with others. Assign shared sandboxes where cross-team visibility is needed.

→ Each channel team operates independently within their resource scope.

Isolating a sensitive campaign

Admin protecting a high-value or confidential campaign

Use object-level access control to apply a label (e.g. C2) to the journey or campaign. Only users whose role carries a matching policy for that label can open the object — even if they have Manage Journeys at the role level.

→ Labelled object is invisible or locked for all users without the matching label policy.

08 Pre-launch Checks

Before You Go Live: What to Verify

Run through these four checks before handing access to your team. Each one catches a different category of misconfiguration — skip one and you'll typically find out about it at the worst possible moment.

✅ Every user has a role assigned

A user added to Admin Console but not assigned to any role in Permissions will see a blank Adobe Journey Optimizer interface with no navigation. Go to Permissions → Roles → [role] → Users and confirm all team members appear in at least one role.

Risk if skipped: User logs in and sees nothing — usually escalated as a "product not working" issue.

✅ Sandbox assignments match environments

Verify that each role's sandbox list matches where the user's work lives. A Campaign Manager without the Production sandbox cannot see or activate campaigns in production. Navigate to Permissions → Roles → [role] → Edit → Sandboxes to confirm the list.

Risk if skipped: User can't see their work in the correct environment — appears as missing data.

✅ Publish permissions intentionally assigned

For roles that need to go live with journeys or campaigns, confirm Publish journey or Manage Campaigns is included. Test by logging in as the user (or using a test account with the same role) and checking whether the Publish button is visible and active.

Risk if skipped: Team is blocked at the final step — can build but not activate, causing delays.

✅ Audit Logs enabled and monitored

Audit logs record every role change, permission update, and significant user action. Confirm they're accessible at Adobe Journey Optimizer → Privacy → Audit Logs. Set up an alert or periodic review cadence so permission changes don't go unnoticed. See audit log docs →

Risk if skipped: Unintended permission escalations go undetected until an incident occurs.

09 Performance

Track Performance After Launch

Once access control is live, here's what to watch in Adobe Journey Optimizer. There's no single "permissions report", but these four signals tell you if your setup is healthy.

🎭 Active roles configured

The total number of roles in Permissions. A healthy number is low — typically 3–8 roles for most organisations. Role sprawl (20+ roles) is a signal that custom roles were created reactively instead of deliberately. Audit and consolidate annually.

👥 Users without a role

Check Permissions → Users for any user listed without a role assignment. This is a blank-access state — the user exists in Admin Console but gets no Adobe Journey Optimizer access. Review and assign roles for all active team members.

📋 Audit log — permission changes

Filter Audit Logs by action type Role to see every role edit, user assignment, and permission change. A spike in role changes is worth investigating — it may indicate unsanctioned access escalation or a role being misused as a workaround.

🚫 Access denied events

In audit logs, filter for Access denied or failed actions by resource. A pattern of denials for a specific user + resource combination means a permission is missing from their role. Resolve proactively to avoid blocked workflows.

Optimisation tips

Review roles quarterly

Set a calendar reminder every quarter to audit role membership. Remove users who've left the team, and check whether any custom roles still match your current team structure. Stale roles are a compliance risk.

Use the built-in roles as a baseline

Before creating a custom role, check whether an existing built-in role covers 90% of the need. Customise only when the difference matters operationally — fewer roles means less maintenance overhead.

Separate Dev and Production sandbox access

Give developers and content builders access to development sandboxes only. Restrict Production sandbox assignments to team leads and admins. This prevents accidental changes to live assets during testing.

Use object labels for high-stakes assets

For campaigns targeting sensitive segments or carrying large budgets, apply an object-level access label. This adds a second layer of protection beyond role-level permissions.

Not seeing expected access? Start here.

User sees blank Adobe Journey Optimizer interface: They have no role assigned in Permissions. Go to Permissions → Roles, find the appropriate role, and add the user under the Users tab.

User can't see a journey or campaign they should have access to: Check whether the object is in a sandbox assigned to their role. Navigate to Permissions → Roles → [role] → Edit → Sandboxes and confirm the correct sandbox is listed. If the object has an object-level label, the user's role also needs a matching label policy.

Publish button missing or greyed out: The user's role is missing the Publish journey permission (for journeys) or Manage Campaigns (for campaigns). Edit the role and add the permission from the Resources panel.

10 Try It

Try It Yourself

🧪
Hands-on scenario

Set up a Campaign Manager role for a new team member

Assign full campaign access and read-only journey access to a new colleague — using a development sandbox to test before touching Production.

1️⃣

Open Permissions and locate the Campaign Manager role

Go to Adobe Experience Cloud → Permissions → Roles. Scroll the role list and click Campaign Manager. Review the current permission and sandbox summary on the role dashboard before editing anything.

2️⃣

Edit the role and verify resource permissions

Click Edit. In the Resources panel, confirm Manage Campaigns is assigned. Locate the Journeys resource — if Manage Journeys is assigned, drag it back to the resource pool and replace it with View Journeys only. This gives read-only journey visibility without edit rights.

3️⃣

Assign a development sandbox to the role

Switch to the Sandboxes tab. Select your development sandbox from the list (do not add Production for this test). Click Save to apply. Confirm the summary shows your development sandbox and the updated permissions.

4️⃣

Add your new team member to the role

From the role dashboard, open the Users tab and click Add user. Type the user's email address, select them from the results, and click Save. The user receives an email invitation with a link to log into Adobe Journey Optimizer.

5️⃣

Verify the access is correct

Ask the user to log in and navigate to Campaigns — they should see the full campaign list and a Create campaign button. Navigate to Journeys — the canvas should load in read-only mode with no edit or publish controls visible. If everything looks right, repeat with the Production sandbox assigned when you're ready to promote them.

✅
You're set up

Your new Campaign Manager can now build and activate campaigns in Adobe Journey Optimizer, see all journeys in read-only mode, and work only within the sandboxes you've designated. When they need Production access, return to the role's Sandboxes tab and add it — no other changes needed.
